## 4. Lacunas de documentação (o que o código faz e nenhum doc conta)

1. **O enforcement estreito não tem doc de arquitetura** `[confirmado]`. O único lugar que diz a verdade operacional — "CPF/CNPJ alone escalates only to effective C → decision `ask` (non-blocking) … the deterministic block is a risk-D tool (`bash_20241022`) at tier:starter, production" — é um runbook de teste local (`docs/runbooks/user-e2e-local.md:14-17`). Nenhum doc voltado a quem constrói sobre o sistema (a UI, por exemplo) declara: só `blocked`/`tool_blocked` produzem 403; `ask/warn/enforce/sandbox_required` encaminham; PII forte não bloqueia no caminho governado; side-effects/preconditions são descartados. A filosofia diz o oposto (§1.6). **Esta é a lacuna nº 1 para a fase de UI** (a apresentação honesta da governança depende dela).
2. **A assimetria de DLP entre `/v1/runs` e `/governed/*` não está documentada** `[confirmado]`. São dois regimes diferentes:
   - `/v1/runs`: `dlpPreScan` lê a config por org `govai.dlp_baseline_config` (`pipeline/dlp.ts:44-49`) e `decidePolicy` pode **negar** (`deny` → run `denied` → 403) ou **redigir** (`mutate` → `redactFindings` aplicado ao input antes do provedor, `run-orchestrator.ts:511-518,575`; findings persistidos `:561-573`; decisão persistida em `govai.policy_decisions`).
   - `/governed/*`: o scan ignora a config da org (closure usa só `detectAllBaseline`, `routes/governed-anthropic.ts:60-71`), **nunca redige** ("We do not redact in this initial governed-native delivery", `handle-messages.ts:219-221`) e registra sempre `action:'warn'` (`:230-240`); o efeito é apenas escalar a classe de risco.
   - Consequência não documentada: uma org que configure `action=deny` para CPF é bloqueada em `/v1/runs` mas tem o MESMO CPF encaminhado por `/governed/anthropic/v1/messages`. Nenhum doc compara os dois caminhos (e `current-state.md:130` ainda rotula o DLP de "scan-only").
3. **Redação e CNPJ — parcialmente coberto** `[confirmado o que existe]`. O CNPJ alfanumérico + a limitação uppercase-only ESTÃO documentados (EP-007: `stale-docs-register.md:74-84`; `regulatory/07`/`24` corrigidos). Já a redação: `redactFindings` (`pipeline/dlp.ts:83-94`) só roda no caminho `/v1/runs`, só sobre os detectores baseline, com substituição `[REDACTED:<detector>]` por índice — nenhum doc descreve o escopo (que o caminho governado NÃO redige) nem o formato. A lacuna real é o item 2 acima visto pela ótica da redação.
4. **O contrato semântico de `credential_source`/`enforcement_decision` não existe em doc nenhum** `[confirmado]`. Os schemas canônicos só exigem string não-vazia (`canonical/govai_pr2_provider_coverage_matrix_v2.md:469`; Peça A `:1268`); o único doc que menciona VALORES (`workroom-governance-room.md:246`) canoniza os literais fixos (§1.11). Quando a fase de correção tornar os campos reais, deveria aterrissar junto uma frase de contrato ("`credential_source` reflete a origem efetiva da credencial resolvida: `tenant_provider_credential` | env/dev | hermetic…"; "`enforcement_decision` é a decisão computada, nunca constante"). Hoje a UI não tem onde ler o que esses campos significam.
5. **`operational_mode`/`tier` como controles de OPERADOR** `[confirmado as buscas; enquadramento deduzido]`. O código faz de `operational_mode` o interruptor-mestre: dev/test desligam enforcement (`enforcement.ts:84-86`), pilot rebaixa (`:89-91`), e o modo comuta o fallback de credencial (`provider-credentials.ts:146-177`). Não existe rota que mute `govai.orgs` (busca por `UPDATE/INSERT govai.orgs` em rotas/pipeline/regulatory: zero) — a mutação é operador-via-SQL, sem trilha de auditoria própria. Fragmentos existem (matriz na Peça A §6.2; fallback no comentário do `.env.example` corrigido no EP-000 rev1, `stale-docs-register.md:44`), mas **nenhum doc declara**: "estes dois campos são plano de operador; não há API nem trilha de mutação; mudá-los altera enforcement e quem paga a credencial". Para a UI isso importa diretamente (badges read-only com consequência explicada).
